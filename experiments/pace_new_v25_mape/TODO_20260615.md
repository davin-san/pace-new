# PACE v25 MAPE Execution TODO

Goal: validate a one-full-system-extraction workflow that transfers traffic to
new network designs while keeping avg and p99 network latency near or below 5%
MAPE against gem5 v25.1 full-system.

## Current Acceptance Gates

- pace-new Garnet source remains byte-identical to gem5 Garnet.
- Changes stay in compat, profile tooling, experiment scripts, or gem5
  instrumentation used only for extracting ground-truth profiles.
- Same-topology profile replay must be below 5% avg and p99 error.
- If predicted-demand transfer fails but oracle-demand transfer passes, the
  demand feedback model is the problem.
- If oracle-demand transfer fails, profile composition or topology replay is
  the problem.

## Current Findings

- Marginal-only phase replay is under-specified and can drop traffic classes.
- Phase-conditioned endpoint/class counts fix dedup phased replay:
  avg `-1.18%`, p99 `+2.69%` versus gem5 T1_inter25.
- Existing four-case demand-ratio MAPE is `3.90%`; dedup is the outlier at
  `12.0%`, but latency transfer still remains below 5%.
- Exact phase extraction initially emitted an empty
  `phase_src_dst_ni_flits_counts_by_vnet` array because
  `PACE_PROFILER_PHASE_TICKS` was set after `m5.instantiate()`. PaceProfiler is
  constructed during Ruby/Garnet instantiation, so the env var must be set
  immediately after CLI parsing and before system objects are built.
- After fixing that extraction-ordering issue, exact phased T0-to-T1 transfer
  across dedup, canneal, and blackscholes plus a dedup T1 self-check reached:
  avg MAPE `1.89%`, p99 MAPE `2.26%`.
  Results:
  `/storage/scratch1/9/daoyama3/pace_new_v25_mape_20260606/pace_flowtiming_eval/exactphase_transfer_envfix_20260615/summary_exactphase_transfer_20260615.csv`.
